03

The loop, made concrete in a client build

This is the payoff, and the reason the last two spine steps matter. The four verbs are not a diagram in the abstract — each one now has a real implementation inside a client engagement’s prototype‑authoring skill. The right column is where the governed loop actually runs on a client’s work.

Verb In Sheerline (the module) In the client prototype skill (executed)
Retrieve Retrieve the system through the MCP, never paste it. One summary resource plus retrieval tools. Step 1 loads DESIGN.md + the DTCG contract (the 70 chrome roles, legal component variants) and declares the target mode. Static contract today; the live MCP is the optional higher‑fidelity gate.
Validate Deterministic, zero‑token checks against the system, not the self‑reported manifest. ds-lint.js wired into Step 6 as a blocking gate: raw hex in chrome, unknown token, off‑scale value, illegal variant, value‑fidelity, sub‑AA pairs, a 12px type floor. Feature colors exempt by marker.
Grade A linter emits a boolean; an evaluator emits a series. Grades inform, never gate. Errors block; warnings stay advisory — density sub‑scale type, tokenless overlays, a missing surface-warning role surface for a designer to read, not auto‑block.
Learn One corrections registry, four readers. A factual correction injects; a behavioral one reminds a human. Two client‑side corrections (the fabrication pattern; the 12px floor and token overlays) logged and promoted into the skill, so they load before the mistake can recur.

Context‑architecture foundations

How the harness governs what enters a session — the Earn the Room discipline, made mechanical.

  • Four‑tier loading. always · skills (procedural) · references (knowledge, on‑demand) · archive. If content is relevant to fewer than half of sessions, it does not load by default.
  • Discovery‑aware selection. A capability registry with semantic search replaces static injection, so an agent finds what it needs by querying intent, not by scanning a pre‑loaded list.
  • Three harness layers. runtime (rented from the vendor) · configuration (HeyHi’s IP) · deployment (the reproducible framework). The line between rented and owned is the one that matters for valuation.
05

The client application, in full

The DS‑MCP onboarding arc proved the loop on two differently‑shaped systems: the practice’s own (the self‑test reproducibility proof) and a client’s real, external one. The client system’s Figma‑native, dark‑canonical shape stress‑tested axes the demo system lacks and exposed three harness gaps. One, G‑ING‑1 (the missing Figma‑Variables adapter), is genuinely unique to that client system; the other two are not, and the practice’s own aliased, multi‑mode system re‑surfaced them independently.

The proof G3: PASS

The ingestion pipeline plus the staged MCP server, run against the client’s real design system: several variable collections, hundreds of variables with alias references, Light and Dark. It converted to DTCG, ingested, derived a 6‑component contract, served an MCP that is the client’s tokens and only the client’s, and the validator caught real drift. All machine conditions met, and the human reviewer signed off on the audit quality. G3: PASS.

  • G‑ING‑1 — no first‑party Figma‑Variables adapter open, high
  • G‑ING‑2 — worksheet did not resolve aliases before contrast fixed in place
  • G‑ING‑3 — single‑mode ingestion; a themed system collapses open, medium

Effort shape for a first onboarding pass this size: about half a day of human judgment, dominated by component behavior authoring and contrast sanctioning, on a seconds‑long mechanical pipeline. That number feeds the service scope.

The prototype‑skill integration executed

The problem was structural: prototypes fabricated values because no canonical source was ever in context and verification had no conformance gate. The fix put a reconciled source in context and added a gate that blocks drift before delivery.

  • Phase 1 — reconciled DESIGN.md to the contract; the DS‑faithful shell is the default, legacy blue quarantined.
  • Phase 2 — ds-lint.js conformance gate wired into Step 6; annotation conventions defined.
  • Phase 4 — corrections logged, freshness + both‑modes notes added.
  • Phase 3 (live MCP) — deferred by design, the linter is the always‑available gate.

Verified end to end: a fabricated value (raw chrome hex, invented token, illegal variant) is caught; a legitimate map feature color is not. A migrated prototype finished at 0 errors, on‑brand in‑browser.
