# ui-studio skill-update proposal: Color as seed-to-palette reasoning (Item 7)

**HeyHi Internal Use Only**

The first build off the ui-styles deep-research program. Promoted into the deployed ui-studio skill on 2026-06-10 (`scripts/palette_gen.py`); `brand.seed_color` was added to `brand-config/schema.json`, and the SKILL.md `Load brand system` step plus the Zone 2 On-Demand table reference this capability.

## What this is

`palette_gen.py` turns ONE seed colour into a structured, accessible-by-construction brand palette. It replaces the subsystem's current colour behaviour — extract once, then freeze, described by a single `warm`/`cool`/`neutral` tag — with the generative seed-to-palette model the research validated (Material HCT + tonal engine; the open-source `material-color-utilities`).

**Smoke-tested:** `python3 palette_gen.py --selftest` → 7 seeds × 2 schemes (light + dark) × 5 documented contrast pairs, all meet WCAG AA. The accessibility guarantee is computed empirically from sRGB luminance, so it holds regardless of perceptual space.

## How it works (and the honest substitution)

- **Perceptual space:** production should use **HCT** (CAM16 × L*) via `material-color-utilities`. That library is not vendored and the build sandbox cannot install it, so this build uses **OKLCH** (self-contained) for hue/chroma identity. The `oklch_*` helpers are the only backend-specific code; swapping them for an HCT backend is the documented upgrade. Role-solving and the WCAG guarantee are backend-agnostic (Provider-Agnostic invariant).
- **Accessible by construction:** the designer picks the seed (the brand colour, the taste); the solver chooses *lightness* per role to hit a WCAG target while preserving the seed's hue/chroma. Identity is chosen by a human; accessibility is solved by the system. That is "infrastructure holds taste," not "infrastructure generates taste."
- **Roles emitted:** `background`, `surface`, `border`, `text` (≥7:1), `text_muted` (≥4.5:1), `accent` + `accent_text` (≥4.5:1), `accent on bg` (≥3:1 UI), plus `primary` and `neutral` tonal ramps.

## Proposed ui-studio / onboarding integration (for review)

1. **Onboarding (`design-system-onboard` / `ui-studio-onboard`, Mode D colour step):** when a seed is known (brand colour, logo, moodboard-dominant), generate `tokens.color` from the seed instead of freezing a flat extraction. Mark generated values in `meta.field_provenance` (e.g. `confidence: generated`).
2. **`brand-config/schema.json`:** add an optional `brand.seed_color` (hex) and allow `tokens.color.*` to carry a `source: "palette_gen"` provenance. No breaking change — generation is opt-in; existing extracted configs are untouched.
3. **`heyhi-style-to-token-reviewer`:** the WCAG and semantic-orphan (±15% saturation) checks become *confirmation* rather than *repair* for generated palettes — they pass by construction. Worth a one-line note in that skill that a `palette_gen` provenance pre-satisfies the contrast checks.

## Open / next (review asks)

- **Dark scheme — BUILT (2026-06-10).** `--scheme dark` solves the same roles against a dark background (a direction-aware contrast solver handles both); maps to `tokens.color.schemes.dark` (ADR-006 Option C). The accent now stays at the seed's natural lightness when WCAG allows (vivid hues keep their identity) and only nudges to satisfy the 3:1 UI rule or to pick a legible text colour — the earlier always-darken behaviour is fixed. Remaining review call: whether dark is generated by default or opt-in per config.
- **Role set.** Confirm the role set above is the right minimum, or extend (e.g. `accent_subtle`, semantic success/warning/error solved against the same bg).
- **Seed selection.** Where does the seed come from when a client gives a logo or moodboard rather than a hex? (Dominant-colour extraction is a separate, smaller build.)
- **HCT swap.** Vendoring `material-color-utilities` (Python port) is the production upgrade; decide whether to vendor or keep OKLCH.
